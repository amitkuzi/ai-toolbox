## D-008 — Cold-start trial mechanism is unreachable because the route query pre-filters it out
Status: accepted

**Sections:** `PRD.md:129` (§5.2, `toolbox-route` reads `store query tools|models --routable`),
`PRD.md:198` (§6.1, `verified` absent ⇒ *candidate*, not *routable*),
`PRD.md:314` (§7.4-C, cold start: "an estimate never outranks a measurement;
`seed-unverified` candidates enter only through a bounded trial").

**Contradiction:** `toolbox-route` only ever queries `--routable` tools/models before
running decisions 1–4. A tool with no `verified` date (i.e. `seed-unverified`) is, by
§6.1's own definition, a *candidate* and explicitly *not* routable. Decision 4's cold-start
clause (7.4-C) assumes such seed-unverified candidates still reach the ranking step so they
can be entered into a bounded trial against the incumbent — but they can never get there,
because the upstream `--routable` filter in §5.2 already excluded them from the query
`toolbox-route` reads. As written, no bounded trial can ever fire through the normal route
flow, and new tools can never graduate out of `seed-unverified`.

**Suggested resolution:** Either (a) have `toolbox-route` query both routable tools and a
bounded slice of top-scored `seed-unverified` candidates (flagged distinctly), or (b) move
the bounded-trial injection into a separate, explicit mechanism (e.g. curator-proposed trial
tasks) and remove the "unchanged from selection-rules.md §2a" framing from 7.4-C that implies
it happens inline during normal ranking.

## D-009 — `plugin` tool type has no path through the category gate
Status: accepted

**Sections:** `PRD.md:182` (§6.1, `type` enum: `script | mcp | skill | subagent | model | plugin | schedule | kb`),
`PRD.md:286-294` (§7.3, category-gate decision table: outputs `kb | schedule | script | mcp | skill | model | subagent`).

**Contradiction:** The tool record schema (§6.1) defines `plugin` as a valid, first-class
`type` value ("how it is invoked — drives decision 3"). But decision 3's gate (03-category-gate.md)
only produces seven possible outputs, and `plugin` is not one of them. Any catalog tool
whose `type` is `plugin` can never be selected by decision 3 → decision 4, because the
gate that is supposed to drive the type choice cannot output that type at all.

**Suggested resolution:** Add a gate question for `plugin` (e.g. "is this itself an
installable Claude Code plugin bundling multiple of the above?") or remove `plugin` from
the `type` enum and treat it as a `category`/`tags` concern instead.

## D-010 — `models.yaml` schema names a raw `my_score` field, contradicting P3's "no editable my_score field"
Status: accepted

**Sections:** `PRD.md:33` (P3: "There is no editable `my_score` field. There are **score events**... `my_score_current` is a *computed* fold"),
`PRD.md:205` (§6.2, `models.yaml` field list: "... `my_score`, `score_samples`, `verified`").

**Contradiction:** §6.1 (tools) carefully names the computed field `my_score_current` and
marks it ⚙ (computed/view-only) precisely to satisfy P3's ban on an editable `my_score`.
§6.2 (models) reintroduces the literal name `my_score` with no ⚙ marker and no
`_current` suffix, in the same schema section that P3 explicitly outlaws. Even if the
intent is that `models.yaml`'s `my_score` is *also* a computed fold, the schema as written
is indistinguishable from the forbidden "editable my_score field," and nothing in §6.2 ties
it to `score.*` events the way §6.1/§6.3 do for tools.

**Suggested resolution:** Rename to `my_score_current` in `models.yaml`, mark it ⚙, and
state explicitly that it folds `model.*`/`score.*` events the same way tools do (or clarify
if models are scored through the same `scores.jsonl` ledger at all — §6.3's example only
shows a tool subject).

## D-011 — Inconsistent requirement for `reason` on initial `tool.added` events
Status: accepted

**Sections:** `PRD.md:170` (§6.0 envelope: "`reason` required on every event **except an
initial `*.added`**"), `PRD.md:36` (§1a: migration `tool.added` events required to carry "a
`reason` citing the source file"), `PRD.md:149` (§5.3 daily-refresh: "append `tool.added` +
`score.seed` (**+reason**)"), `PRD.md:349` (§8, `/toolbox:add`: "append `tool.added` /
`source.added` with `via: ui-manual` **+ reason**").

**Contradiction:** The binding envelope rule (P4, §6.0) carves out an explicit exception:
initial `*.added` events do not require a `reason`. Yet every single concrete instance of a
`tool.added` event described elsewhere in the PRD (migration, daily curator discovery, and
the manual `/toolbox:add` command) mandates a `reason`. The stated general rule is never
actually exercised anywhere in the document — which means either the exception is dead
language that should be removed, or there exists an unstated case where `tool.added` truly
has no reason that isn't documented, leaving CI (NF-2, which enforces "reason... where
required") unable to know which behavior is authoritative.

**Suggested resolution:** Drop the "except an initial `*.added`" carve-out from §6.0 and
require `reason` on every event unconditionally (matching actual practice everywhere else),
or if the exception is intentional (e.g. only for bulk catalog seeding with no discoverable
source), name that one case explicitly instead of leaving it as an unqualified exception.

## D-012 — `rules_version` has no defined source of truth
Status: accepted

**Sections:** `PRD.md:172` (§6.0: "`rules_version` — `decision` only: `rules/` semver +
short hash"), `PRD.md:92-100` (§5.1 repo layout, `rules/` directory listing — no version
manifest, `VERSION` file, or `CHANGELOG` under `rules/`).

**Gap:** Every `decision` event must stamp a `rules_version` (semver + short hash) per the
binding envelope (P4/P2), and the worked example in §6.3 shows `"rules_version":"1.0.0+a1b2c3"`.
But §5.1's repo layout never defines where that semver comes from — there's no versioned
manifest file inside `rules/`, and the "hash" presumably means a git commit hash of the
`rules/` tree, but that's never stated. `store.py` (§5.1) is not described as computing this
either. Without a defined mechanism, different implementations (or backends) could compute
`rules_version` inconsistently, breaking P2's traceability guarantee that `/toolbox:trace`
can show "which catalog events were in force at that moment."

**Suggested resolution:** State explicitly in §5.1 or §6.0 how `rules_version` is derived
(e.g. a `rules/VERSION` file bumped on any rule change, combined with `git rev-parse --short HEAD -- rules/`
computed by `store.py` at decision-append time).

## D-013 — Two divergent "current score" formulas (`my_score_current` vs `my_score_ctx`) with no reconciling definition
Status: accepted

**Sections:** `PRD.md:195` (§6.1: `my_score_current` = "fold of `score.*` events (EMA + decay + human × 1.5)"),
`PRD.md:312` (§7.4-B: `my_score_ctx` = "weighted mean of outcome scores for this tool:
same `task_type` × 1.0, adjacent × 0.5, any × 0.25; `human:*` × 1.5; decay after 90 days"),
`PRD.md:322-329` (§7.5: "Score projection... `my_score_current = EMA(α=0.3, by ts) with
90-day decay, human × 1.5`").

**Contradiction/gap:** Two different scores, computed by two different algorithms, both
claim to represent "the tool's current score, folded from outcome events, decayed after
90 days, human-weighted 1.5×." `my_score_current` (§6.1, §7.5) is a plain time-decayed EMA
across *all* outcomes regardless of task type. `my_score_ctx` (§7.4-B, used inside the
`effective` ranking formula) is a task-type-relevance-weighted mean (1.0 / 0.5 / 0.25 by
task-type match) with no EMA. The PRD never states whether these are the same computation
described loosely twice, or genuinely two separate numbers that coexist — and if the
latter, which one feeds `views/scores-summary.yaml`'s `by_task_type` breakdown (§6.3),
and whether `rescore.py` computes one, both, or is expected to derive `my_score_ctx`
on-the-fly per query (since it's context-dependent per task type and can't be precomputed
into a single view field the way `my_score_current` can).

**Suggested resolution:** Either merge into one formula (task-type-weighted EMA with
decay and human weighting) used everywhere, or explicitly name them as two distinct,
independently-defined quantities — a global `my_score_current` (shown in views, EMA-based)
and a per-query `my_score_ctx` (computed live by the ranking step, not stored in a view) —
and say so in both §6.1 and §7.4.
